# BrowserGateway 定时任务模块设计说明书

## 1. 概述

### 1.1 模块定位
定时任务模块是BrowserGateway项目的核心监控与管理组件,负责执行周期性的系统健康检查、资源清理、状态上报等后台任务,确保系统的稳定运行和资源的有效利用。

### 1.2 设计目标
- **资源监控**: 实时监控浏览器实例、TCP连接、系统资源状态
- **自动清理**: 自动清理过期、失效的资源实例
- **健康检查**: 定期检查系统CPU、内存、网络等关键指标
- **状态上报**: 定期上报服务实例状态和使用情况
- **日志管理**: 定期执行日志轮转脚本

## 2. 模块架构

### 2.1 任务列表
定时任务模块包含以下7个定时任务:

| 任务名称 | 类名 | 执行周期 | 主要功能 |
|---------|------|---------|---------|
| 浏览器状态检查任务 | BrowserCheckTask | 1800000ms(30分钟) | 检查浏览器实例健康状态,清理失效实例 |
| 浏览器关闭任务 | BrowserCloserTask | 600000ms(10分钟) | 关闭过期、无连接的浏览器实例 |
| 浏览器代理日志转储任务 | BrowserProxyLogDump | 3600000ms(60分钟) | 执行日志轮转脚本 |
| 健康检查任务 | HealthCheckTask | 60000ms(1分钟) | 检查CPU、内存、网络状态并告警 |
| 服务上报任务 | ServiceReporter | 应用启动时触发 | 上报链端点信息,支持重试机制 |
| 服务状态刷新任务 | ServiceStatusRefresherTask | 30000ms(30秒) | 上报服务使用状态 |
| TCP通道监控任务 | TcpChannelMonitor | 600000ms(10分钟) | 监控并清理过期TCP连接 |

## 3. 详细设计

### 3.1 浏览器状态检查任务 (BrowserCheckTask)

#### 3.1.1 功能描述
定期调用浏览器驱动服务的健康检查接口,识别失效的浏览器上下文(Context),并清理对应的浏览器实例。

#### 3.1.2 执行流程
```
1. 调用 client.browser().healthCheck() 获取健康检查结果
2. 如果检查成功,直接返回
3. 如果检查失败,获取所有用户实例
4. 遍历用户实例,检查其proxyContextId是否在errContexts列表中
5. 将失效的用户实例添加到删除列表
6. 批量删除失效实例
```

#### 3.1.3 配置参数
- `browsergw.scheduled.check-browser-period`: 执行周期,默认1800000ms(30分钟)
- `browsergw.chrome.endpoint`: 浏览器驱动服务端点地址

#### 3.1.4 关键接口
```java
// 浏览器驱动健康检查接口
Type.HealthCheckResult client.browser().healthCheck()

// 返回结果结构
class HealthCheckResult {
    boolean success;           // 检查是否成功
    List<String> errContexts;  // 失效的Context ID列表
}
```

#### 3.1.5 异常处理
- 整个任务执行过程包含在try-catch块中
- 异常时记录错误日志但不中断定时任务
- 使用日志记录任务执行耗时和清理的实例列表

### 3.2 浏览器关闭任务 (BrowserCloserTask)

#### 3.2.1 功能描述
定期检查浏览器实例的活跃状态和心跳时间,关闭过期或无连接的浏览器实例。

#### 3.2.2 执行流程
```
1. 获取所有用户ID列表
2. 遍历每个用户ID:
   a. 获取用户的UserBind信息
   b. 检查实例是否活跃(isActive)
   c. 检查实例是否超时(ifExpired)
   d. 如果不活跃或超时,删除浏览器实例
```

#### 3.2.3 活跃状态判断逻辑
```java
private boolean isActive(UserBind userBind) {
    // 1. UserBind对象不能为空
    if (userBind == null) return false;
    
    // 2. browserInstance不能为空
    if (userBind.getBrowserInstance() == null) return false;
    
    // 3. browserInstance必须等于本机地址
    if (!config.getSelfAddr().equals(userBind.getBrowserInstance())) return false;
    
    // 4. heartbeats不能为空
    if (userBind.getHeartbeats() == null) return false;
    
    return true;
}
```

#### 3.2.4 超时判断逻辑
```java
private boolean ifExpired(String userId) {
    // 当前时间纳秒值 - 心跳时间纳秒值 > TTL
    return System.nanoTime() - chromeSet.getHeartbeats(userId) > ttl;
}
```

#### 3.2.5 配置参数
- `browsergw.scheduled.close-browser-period`: 执行周期,默认600000ms(10分钟)
- `browsergw.chrome.ttl`: 浏览器实例超时时间,默认360000000000ns(100小时)

#### 3.2.6 异常处理
- 每个用户的处理独立进行,单个用户异常不影响其他用户
- 异常时记录错误日志,包含用户ID
- 整体任务异常时记录日志但不中断定时任务

### 3.3 浏览器代理日志转储任务 (BrowserProxyLogDump)

#### 3.3.1 功能描述
定期执行Shell脚本,实现日志文件的轮转和清理。

#### 3.3.2 执行流程
```
1. 构建ProcessBuilder,配置执行bash命令
2. 合并错误输出到标准输出
3. 启动进程并读取输出流
4. 逐行记录脚本输出到日志
5. 等待进程执行结束,获取退出码
6. 根据退出码判断执行结果并记录日志
```

#### 3.3.3 配置参数
- `shell.script.path`: Shell脚本路径,默认/opt/csp/browsergw/module/log_rotate.sh
- `shell.script.period`: 执行周期,默认3600000ms(60分钟)

#### 3.3.4 异常处理
- 脚本执行异常时记录错误日志
- 脚本退出码非0时记录警告日志
- 异常不影响定时任务的继续执行

### 3.4 健康检查任务 (HealthCheckTask)

#### 3.4.1 功能描述
采用策略模式实现多维度系统健康检查,包括CPU使用率、内存使用率、网络接口状态,检查结果用于告警和服务状态上报。

#### 3.4.2 检查策略
| 策略名称 | 检查项 | 触发阈值 | 恢复阈值 |
|---------|-------|---------|---------|
| CpuUsageCheck | CPU使用率 | 90% | 80% |
| MemoryUsageCheck | 内存使用率 | 90% | 80% |
| NetWorkInterfaceCheck | 网络接口状态 | bond-base、bond-external必须存在且UP | - |

#### 3.4.3 执行流程
```
1. 初始化检查策略列表(CPU、内存、网络)
2. 执行check()方法:
   a. 遍历所有检查策略
   b. 调用每个策略的check()方法
   c. 聚合检查结果,设置整体健康状态
3. 执行report()方法:
   a. 构建健康检查结果Map
   b. 根据健康状态发送或清除告警
   c. 上报实例属性到服务管理中心
```

#### 3.4.4 CPU/内存检查逻辑
```java
// 带滞后的阈值判断逻辑
if(inHighUsage) {
    // 已处于高负载状态,需要降至恢复阈值才认为健康
    result.setHealthy(usage < recoverThreshold);
} else {
    // 正常状态,超过触发阈值才认为不健康
    result.setHealthy(usage < triggerThreshold);
}
inHighUsage = !result.isHealthy();
```

#### 3.4.5 网络接口检查逻辑
```java
// 检查指定网络接口是否存在且处于UP状态
for (String name : interfaceList) {
    NetworkInterface ni = NetworkInterface.getByName(name);
    if (ni == null || !ni.isUp()) {
        isHealthy = false;
        errMsg.append(String.format("interface %s is down;", name));
    }
}
```

#### 3.4.6 配置参数
- `browsergw.scheduled.health-check-period`: 执行周期,默认60000ms(1分钟)
- `browsergw.healthCheck.cpu-trigger-threshold`: CPU触发阈值,默认90
- `browsergw.healthCheck.cpu-recover-threshold`: CPU恢复阈值,默认80
- `browsergw.healthCheck.memory-trigger-threshold`: 内存触发阈值,默认90
- `browsergw.healthCheck.memory-recover-threshold`: 内存恢复阈值,默认80

#### 3.4.7 告警机制
- 告警类型: ALARM_300032 (亚健康检查)
- 健康状态: 清除告警,消息"Sub‑healthy health check passed"
- 不健康状态: 发送告警,消息"Sub‑health check failed"

#### 3.4.8 状态上报
```java
Map<String, String> healthResult = new HashMap<>();
healthResult.put("isHealthy", Boolean.toString(isHealthy));
healthResult.put("checkMsg", checkErrMsg);
serviceManagementAdapter.reportInstanceProperties(healthResult);
```

### 3.5 服务上报任务 (ServiceReporter)

#### 3.5.1 功能描述
在应用启动时上报链端点信息,确保服务实例注册到服务管理中心。采用Spring事件监听机制,在应用上下文刷新完成后自动触发,支持失败重试。

#### 3.5.2 执行流程
```
1. 监听Spring ContextRefreshedEvent事件
2. 调用 reportChainInfoWithRetry(5) 启动带重试的上报流程
3. 调用 chromeSet.reportChainEndpoints() 上报链端点信息
4. 如果上报成功,记录成功日志并返回
5. 如果上报失败且剩余重试次数为0,记录FATAL日志并返回
6. 如果上报失败且仍有重试次数,等待30秒后递归重试
```

#### 3.5.3 触发方式
与其他定时任务不同,ServiceReporter不使用周期性调度器,而是通过Spring事件机制在应用启动时触发:
```java
@EventListener(ContextRefreshedEvent.class)
public void startReport(ContextRefreshedEvent event) {
    reportChainInfoWithRetry(5);
    log.info("finish report chain endpoints");
}
```

#### 3.5.4 重试机制
```java
private void reportChainInfoWithRetry(int remainCount) {
    long waitTime = 30000; // 30秒间隔
    
    if (chromeSet.reportChainEndpoints()) {
        return; // 上报成功
    }
    
    if (remainCount == 0) {
        log.fatal("report chain endpoint failed"); // 达到最大重试次数
        return;
    }
    
    Thread.sleep(waitTime); // 等待30秒后重试
    reportChainInfoWithRetry(remainCount - 1);
}
```

#### 3.5.5 重试参数
- 最大重试次数: 5次
- 重试间隔: 30000ms(30秒)
- 最大等待时间: 5 × 30s = 150s(2.5分钟)

#### 3.5.6 关键接口
```java
// 上报链端点信息
boolean chromeSet.reportChainEndpoints()
// 返回值: true-上报成功, false-上报失败
```

#### 3.5.7 异常处理
- 上报失败时进行递归重试,最多重试5次
- Thread.sleep被中断时记录FATAL级别日志
- 达到最大重试次数仍失败时记录FATAL级别日志,表明依靠自身重试无法恢复

### 3.7 TCP通道监控任务 (TcpChannelMonitor)

#### 3.7.1 功能描述
监控控制通道和媒体通道的TCP连接心跳时间,清理超时的连接。

#### 3.7.2 执行流程
```
1. 获取心跳超时时间ttl
2. 检查控制通道(ControlClientSet)的心跳
3. 检查媒体通道(MediaClientSet)的心跳
4. 对每个通道:
   a. 遍历所有客户端
   b. 检查心跳时间是否超时
   c. 收集超时的客户端ID
   d. 批量删除超时客户端
```

#### 3.7.3 心跳超时判断
```java
// 当前时间纳秒值 - 客户端心跳时间纳秒值 > TTL
if (System.nanoTime() - client.getTime(Client.VAL_HEARTBEAT_TIME) > ttl) {
    deleteKeys.add(key);
}
```

#### 3.7.4 配置参数
- `browsergw.scheduled.tcp-heartbeat-period`: 执行周期,默认600000ms(10分钟)
- `browsergw.tcp.heartbeat-ttl`: TCP连接心跳超时时间,默认360000000000ns(100小时)

#### 3.7.5 客户端时间戳类型
```java
public class Client {
    public static final String VAL_HEARTBEAT_TIME = "heartTime";  // 心跳时间
    public static final String VAL_UPDATE_TIME = "updateTime";    // 更新时间
    public static final String VAL_START_TIME = "startTime";      // 开始时间
}
```

#### 3.7.6 异常处理
- 整体任务异常时记录错误日志但不中断定时任务

## 7. 生命周期管理

### 7.1 初始化流程
所有定时任务采用统一的初始化模式:
```java
@PostConstruct
public void init() {
    // 1. 创建单线程调度器
    scheduler = Executors.newSingleThreadScheduledExecutor();
    
    // 2. 立即执行第一次任务,之后按固定周期执行
    scheduler.scheduleAtFixedRate(this::taskMethod, 
                                  0,           // 初始延迟
                                  period,      // 执行周期
                                  TimeUnit.MILLISECONDS);
}
```

### 7.2 销毁流程
所有定时任务采用统一的销毁模式:
```java
@PreDestroy
public void destroy() {
    // 优雅关闭调度器
    if (scheduler != null) {
        scheduler.shutdown();
    }
}
```

### 7.3 Spring事件监听
ServiceReporter使用Spring事件机制启动,不同于其他定时任务的周期性调度模式:
```java
@Service
public class ServiceReporter {
    @EventListener(ContextRefreshedEvent.class)
    public void startReport(ContextRefreshedEvent event) {
        reportChainInfoWithRetry(5);
        log.info("finish report chain endpoints");
    }
}
```

## 8. 异常处理策略

### 8.1 任务级异常处理
- 每个定时任务的执行方法都包含在try-catch块中
- 异常时记录错误日志,包含堆栈信息
- 异常不影响定时任务的继续执行

### 8.2 子任务级异常处理
- BrowserCloserTask: 每个用户的处理独立进行,单个用户异常不影响其他用户
- HealthCheckTask: 每个检查策略独立执行,单个策略异常不影响其他策略

### 8.3 重试机制
ServiceReporter实现重试机制:
```java
private void reportChainInfoWithRetry(int remainCount) {
    long waitTime = 30000; // 30s间隔
    if (chromeSet.reportChainEndpoints()) {
        return;
    }
    if (remainCount == 0) {
        log.fatal("report chain endpoint failed");
        return;
    }
    Thread.sleep(waitTime);
    reportChainInfoWithRetry(remainCount - 1);
}
```

## 10. 线程安全设计

### 10.1 调度器线程模型
- 每个定时任务使用独立的单线程调度器
- 使用 `Executors.newSingleThreadScheduledExecutor()` 创建
- 确保同一定时任务的串行执行

### 10.2 共享资源访问
- `IChromeSet`: 提供并发安全的浏览器实例管理
- `ClientSet`: 提供并发安全的TCP客户端集合管理
- 使用 `ConcurrentHashMap` 等并发容器保证线程安全

### 10.3 时间精度
- 使用 `System.nanoTime()` 进行纳秒级时间计算
- 心跳超时判断使用纳秒时间戳避免精度丢失

## 11. 性能考虑

### 11.1 执行周期设计
| 任务 | 周期 | 设计理由 |
|-----|------|---------|
| HealthCheckTask | 1分钟 | 快速发现系统异常,及时告警 |
| ServiceStatusRefresherTask | 30秒 | 频繁上报保证状态实时性 |
| ServiceReporter | 应用启动时触发(重试间隔30秒,最多5次) | 启动时一次性上报链端点,确保服务注册成功 |
| BrowserCloserTask | 10分钟 | 平衡资源清理和用户体验 |
| TcpChannelMonitor | 10分钟 | 平衡连接监控和性能开销 |
| BrowserCheckTask | 30分钟 | 浏览器健康检查开销较大,降低频率 |
| BrowserProxyLogDump | 60分钟 | 日志轮转不需要高频执行 |

### 11.2 批量操作优化
- BrowserCheckTask: 先收集所有失效用户,再批量删除
- TcpChannelMonitor: 先收集所有超时客户端,再批量删除
- 减少锁竞争,提高执行效率

### 11.3 资源清理策略
- 优先清理明显失效的实例(无心跳、无连接)
- 使用滞后阈值避免频繁告警
- 优雅关闭调度器,避免资源泄漏
